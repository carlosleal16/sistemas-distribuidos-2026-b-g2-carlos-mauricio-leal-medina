Qué es TDD

Primero la prueba,
después el código

Test-Driven Development: antes de escribir una función, escribimos la prueba que describe lo que debe hacer. El código existe solo para hacer pasar esa prueba.

TDD significa Test-Driven Development, desarrollo guiado por pruebas. La idea central es invertir el orden normal: no programo y luego pruebo, sino que primero escribo la prueba y después el código que la hace pasar.

El ciclo

Rojo → Verde → Refactor

1 · ROJO

Escribo la prueba

Describe un comportamiento que aún no existe. Se ejecuta y falla.

2 · VERDE

Código mínimo

Lo justo para que la prueba pase. Nada de adornos.

3 · REFACTOR

Limpio el código

Mejoro nombres y estructura. Las pruebas confirman que nada se rompió.

El ciclo es corto, de minutos. Rojo: escribo una prueba y veo que falla, eso demuestra que la prueba sirve. Verde: escribo el mínimo código para que pase. Refactor: limpio sin cambiar el comportamiento, con las pruebas como red de seguridad. Y repito con el siguiente comportamiento.

Por qué usarlo

Lo que ganamos

Diseño más simple

Si es fácil de probar, está bien desacoplado.

Refactor sin miedo

Las pruebas avisan al instante si algo se rompe.

Documentación viva

Cada prueba dice qué hace el sistema, y nunca se desactualiza.

Evidencia de calidad

Pruebas publicadas y corriendo en CI: lo que la norma puede verificar.

Cuatro beneficios. El diseño sale más simple porque el código tiene que poder probarse aislado. Podemos refactorizar con confianza. Las pruebas documentan el comportamiento. Y para nosotros es evidencia concreta de calidad, porque en el curso solo cuenta lo publicado.

Un ciclo sobre la agenda del barbero

1 · ROJO: la prueba (falla)

@Test
void reservarOcupado_debeRechazar() {
  var agenda = new Agenda(barbero);
  agenda.reservar(cita("10:00"));
  assertThrows(HorarioOcupado.class,
    () -> agenda.reservar(cita("10:00")));
}

2 · VERDE: el código mínimo

public void reservar(Cita cita) {
  if (estaOcupado(cita.horario()))
    throw new HorarioOcupado();
  citas.add(cita);
}

3 · Refactor: por ejemplo, extraer estaOcupado() a un objeto Horario. La prueba sigue en verde.

En BarberSaaS · paso 3

Las pruebas también respetan la arquitectura

Regla 7

El esquema vive en el -db. Las pruebas de integración usan sus migraciones; el -api no crea tablas propias.

Regla 8

Si citas necesita datos de clientes, la prueba simula la API de clientes. Nunca toca su base.

Contratos

Las pruebas de contrato garantizan que esos mocks coinciden con el OpenAPI real de 07-api.

TDD no es excusa para saltarse la arquitectura. Regla 7: el esquema vive en el repo -db, así que las pruebas de integración del -api usan esas migraciones. Regla 8: cada dominio consulta solo su base; si citas necesita clientes, en la prueba simulamos la API de clientes. Y las pruebas de contrato aseguran que esa simulación corresponde al contrato publicado.

En BarberSaaS · paso 4

Más allá del -api

-workflow (sagas)

Primero las pruebas del flujo de 16-bpmn: camino feliz, fallo en cada paso y su compensación.

-worker

“Dado este evento, ocurre este efecto”. Y procesarlo dos veces no lo duplica (idempotencia).

-front y -app

TDD en la lógica y validaciones: “sin hora, muestra error”. En lo visual no compensa.

También aplica fuera de las APIs. En las sagas del -workflow probamos primero el flujo de BPMN, incluyendo fallos y compensaciones. En los workers, que un evento produzca su efecto y que repetirlo no lo duplique. En el front, aplicamos TDD a la lógica y validaciones; el diseño visual no se presta tanto.

El ciclo queda visible en Git y en CI

test: reserva rechaza horario ocupado

feat: validar solapamiento en Agenda.reservar

refactor: extraer objeto Horario

El ci.yml de cada repo corre las pruebas en cada PR: si fallan, no se fusiona. El historial sirve como evidencia para el hu-status semanal.

El ciclo deja rastro en el historial de la rama: un commit de prueba, uno de funcionalidad y uno de refactor. El pipeline de CI corre las pruebas en cada PR y bloquea el merge si fallan. Y ese historial es evidencia real para nuestro reporte semanal.

Cómo lo aplicamos

TDD en los 8 dominios, no solo en uno

01

Cada dominio convierte los criterios de sus HU en pruebas

02

TDD en el dominio y los casos de uso de cada -api

03

Pruebas de contrato entre dominios, según 07-api

04

Las pruebas corren en el ci.yml de cada repo: si fallan, no hay merge

05

Las mismas convenciones de pruebas en todos los dominios

TDD no se aplica en un solo dominio, sino en los 8. Cada dominio toma sus historias de usuario y convierte los criterios de aceptación en pruebas. Aplicamos TDD en el dominio y los casos de uso de cada -api. Como los dominios se comunican solo por API, agregamos pruebas de contrato basadas en 07-api. Las pruebas corren en el CI de cada repo y bloquean el merge si fallan. Y todos los dominios siguen las mismas convenciones, así cualquiera del equipo entiende las pruebas de otro dominio.
